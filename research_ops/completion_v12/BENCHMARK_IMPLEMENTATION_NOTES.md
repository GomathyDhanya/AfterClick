# V12 benchmark implementation and qualification notes

This is a constructed compositional benchmark. It does not claim 216 human-
authored enterprise applications, independent human review, or unseen business
ontologies. Six consequence families share business operators and policy
vocabulary. Eight different dependency architectures at three horizons produce
24 structural layouts: six TEST and two DEV architectures per horizon. TEST
and DEV have no identical operation-kind/dependency/conditional-rule layout.
Public business rules are shared; language-only generalization is not claimed.
These limitations must accompany statistical inference over source contracts.

The candidate v6 directory contains 72 DEV and 216 TEST contracts, each with a
specific obligation graph, public policy, scope evidence, authorization case,
role requirements, receiver type, and restoration records. These are candidate
contracts until their external qualification certificates pass. The original
single-resource prototype and its registry are preserved separately; repeated
IDs across prototype/benchmark versions are disambiguated by contract hash.

FlowBoard uses its versioned core tasks, dependency edges, approval comments,
summary/readiness jobs, notification outbox, and additional normalized
capability grants. OpsConsole independently uses work orders, role signoffs,
JSON inventory assets, and scoped services. Only audit/receiver/transport and
presentation helpers are shared. The frozen FlowBoard domain remains unchanged;
a versioned copy fixes a fan-out notification identity collision exposed by the
larger graphs. Reference witnesses exercise the ordinary visible interface.

Intermediate administrative duties are persisted scope-bearing business
records. The benchmark does not simulate every underlying enterprise process
named by those records. Irreversible duties are independently realized by a
loopback HTTP receiver: notification inboxes, delegated document observations,
nonrefundable resource debits, consented/restricted export records, and external
service versions. Local corrections cannot delete these immutable records.
L3 has two separately queued external duties, with the second dependent on
verified receipt of the first. Distinct restoration duties change separate
capability/service objects rather than only task labels.

Conditional classifications arrive after the source cut. Role approvers and a
collaborator operate independently of actor inference. Two conditional scope
rules require current signed evidence. Selected pending requests reveal their
signed authorization only through public verification. An approved pending
request is mandatory, so cancel-everything is not a safe completion policy.
Approval expiration is enforced before dispatch and does not invalidate work
already authorized and dispatched. A protected pending request must be
reconciled and legitimate service restored.

Qualification uses a separately declared feasible admission schedule (base
3000 ms with seeded jitter); it does not certify every tight stress world as
solvable. Workers log nominal eligibility, actual admission, physical receiver
commit, and public verification separately. A SQL audit event occurs before
transaction commit; the returned command timestamp is an upper bound after
commit. Neither is falsely labeled the exact commit instant.

Failed versions and all started attempts remain under v12-06/v12-07 artifact
runs. Earlier polling replaced buttons, and a 5-second browser response limit
was shorter than observed successful responses under load. Stable keyed DOM
nodes, bounded 15-second input responses, reduced polling, and keyboard
activation are qualified separately. Infrastructure failures are retained, not
converted to agent failures or silently replaced by favorable outcomes.

No TEST model outcome is opened by reference qualification or oracle mutation
checks. The protocol remains unfrozen until all task witnesses, independent
oracle challenges, DEV calibration, regression and power/feasibility gates are
complete. No claim of research completion follows from this document.
